Summary:
The paper introduces a Persistent Shared Memory (PSM) setting for zero-shot object navigation (ZSON), enabling single or multiple agents to accumulate and reuse scene knowledge across sequential tasks within the same environment (Section 3.1, Fig. 1). It realizes PSM with a Temporally Consistent Semantic Map (TCSM), an explicit sparse 3D voxel map that maintains per-voxel semantic dictionaries and updates them via confidence-weighted aggregation to mitigate drift and noise (Section 3.3; Eq. 1–2; Fig. 2). On top of this memory, the authors propose a beyond-line-of-sight (BLOS) navigation strategy that selects proxy goal regions by line-of-sight checks and “broadcasts” target semantics to reachable areas, enabling efficient planning toward occluded or distant objects (Section 3.4; Eq. 6–9). Experiments on HM3D and MP3D show state-of-the-art ZSON performance, notably improving SR/SPL/SuccSPL over prior methods (Table 1), with gains that increase as the pre-existing memory grows (Fig. 3). The framework supports collaborative multi-agent operation with a shared TCSM, yielding large boosts over stateless baselines (Table 2). Ablations validate the contributions of TCSM, confidence-weighted updates, and BLOS planning, and report sensitivity to segmentation backbones and γ (Section 4.5; Table 3–4). A computation analysis demonstrates near-linear scaling of update/query costs with voxel count and provides practical resource profiles (Section 4.6; Table 5).

Strengths:
1. Clear, impactful problem redefinition. The paper formalizes a Persistent Shared Memory (PSM) setting that reframes ZSON from isolated, stateless episodes to continual, cross-task and multi-agent operation within the same environment (Section 3.1; Fig. 1), directly addressing redundant re-exploration that existing ZSON pipelines ignore.

2. Well-specified, robust memory representation. The Temporally Consistent Semantic Map (TCSM) is a precise, implementation-ready construct: a sparse voxel grid with per-voxel semantic dictionaries and a confidence-weighted update rule (Section 3.3; Eq. 1–2). This design decouples scene memory from task logic and counteracts “semantic drift” via “weighted confidence updates,” a concrete fix to brittleness in prior explicit semantic maps.

3. Principled handling of occlusion via BLOS planning. The beyond-line-of-sight strategy introduces a LoS-restricted proxy-goal region and “broadcasts” target semantics into reachable space (Section 3.4; Eq. 6–9, “Broadcasted Value Map Construction”). This is a crisp, algorithmic solution to occluded or disconnected targets that traditional LoS-only methods cannot exploit.

4. Strong empirical validation with state-of-the-art results. On HM3D and MP3D, the method achieves top SR/SPL/SuccSPL among ZSON approaches (Table 1), with particularly notable SPL/SuccSPL gains that align with the claim of reduced redundant exploration.

5. Convincing evidence that persistent memory matters. Performance scales systematically with pre-existing memory size and saturates as coverage increases (Fig. 3), including a careful “read‑only” TCSM test to isolate the benefit of prior knowledge (Section 4.3).

6. Multi-agent practicality and insight. A single shared TCSM delivers large improvements over stateless baselines across 1/2/4 agents (Table 2), and the paper articulates the throughput–per-task trade-off under parallel execution (Section 4.4), demonstrating thoughtful system-level analysis.

7. Targeted ablations that attribute gains. The stepwise comparison shows the specific contributions of TCSM, confidence-weighted updates, and BLOS planning on SR/SPL/SuccSPL (Table 3), rather than presenting a monolithic system-level gain.

8. Systems realism and scalability analysis. The sparse representation “ensures memory scales only with the explored volume” and supports efficient queries (Section 3.3), while compute profiling quantifies near-linear dependence on voxel count and provides concrete resource/time budgets (Table 5).

9. Careful metric design to assess path efficiency. Reporting SuccSPL = SPL/SR (Section 4.1) helps decouple path optimality from success rate, strengthening claims about efficiency beyond raw SR.

10. Clean integration of perception, mapping, and LLM/VLM planning. The pipeline bridges a global, task-agnostic memory (TCSM) to a short-term value-map planner via structured point clouds and DCoN (Fig. 2; Section 3.4), a creative, well-engineered combination that advances zero-shot embodied navigation beyond myopic frontiers.

Weaknesses:
1. Apples-to-oranges main comparison (persistent vs. stateless). The SOTA claims in Table 1 pit a memory-persistent system against baselines that “reset their state for each new episode” (Section 4.2). This confounds algorithmic advances with the advantage of persistent memory. Actionable: (a) add a stateless variant of your pipeline to Table 1; (b) add memory-enabled baselines (e.g., InstructNav and VLFM augmented with any persistent map they already maintain, or with your TCSM but without BLOS) to quantify the net gain attributable to PSM/TCSM/BLOS; (c) report all under identical evaluation protocols and step budgets.

2. Inconsistent and ambiguous ablations hinder attribution. Table 3 contains duplicate labels and contradictory entries (two “InstructNav*”; two “TCSM+Weighted Update+Full Strategy” with very different SR/SPL/SuccSPL), and the “PSM Setting” column is unlabeled/unused. This prevents a clean read of each module’s contribution (Section 4.5). Actionable: fix table labels; clearly specify which rows are with/without PSM, weighted vs. replacement updates, and base vs. full (BLOS) strategy; ensure each row appears once and is evaluated on the same episodes.

3. γ reporting conflicts and tuning opacity. γ is set to 0.2 in Implementation Details (Section 4.1), while the text later claims “0.8 yielded the most favorable results,” yet Table 4 shows GLEE at γ=0.2 (and “GLEE (Wu et al., 2024) 0.2”) as the best or tied-best SR/SPL. Actionable: reconcile these discrepancies, document the tuning protocol, and standardize γ across all main results; if γ differs by dataset/backbone, state so and justify.

4. Limited rigor of the confidence fusion rule. The TCSM update in Eq. (2) is a fixed-rate exponential blend of per-pixel confidences regardless of observation count, class imbalance, or uncertainty calibration. It lacks normalization/priors, does not downweight outliers, and can over‑reinforce systematic biases or repeated mis-segmentations. Actionable: (a) evaluate probabilistic or count-based fusion (e.g., per‑class evidence accumulation with normalization/decay); (b) add map‑level uncertainty (entropy/variance) and use it in planning; (c) add time-decay/forgetting to mitigate stale or drifting labels.

5. No direct evaluation of “semantic drift” robustness. The paper claims TCSM “combats semantic drift” via weighted updates (Introduction; Section 3.3), but evidence is indirect (Table 3 shows gains over replacement). There is no stress test under noisy segmentation or long-horizon accumulation. Actionable: (a) inject controlled label noise or confusion into the segmentation outputs and plot SR/SPL/SuccSPL vs. noise; (b) evaluate map accuracy (per‑voxel semantic precision/recall against ground-truth meshes) over time; (c) run long rollouts (many tasks per scene) to quantify drift and catastrophic corruption rates.

6. BLOS LoS computation relies on fragile wall extraction. The LoS check (Eq. 6) depends on PC_wall derived from heuristic processing of TCSM (Section 3.4, “Short-term memory”), which may yield false positives/negatives if walls are incomplete or noisy. Actionable: (a) replace or augment LoS with occupancy/mesh ray casting directly in the voxel grid; (b) add an oracle LoS ablation (using perfect walls from simulator mesh) to quantify the headroom; (c) report how often BLOS is triggered, its success delta vs. base, and failure modes when LoS is misestimated.

7. Multi-agent evaluation lacks systems realism. Table 2 shows SR/SPL gains with shared TCSM, but omits communication/computation constraints, staleness, or contention in concurrent updates (Section 4.4). Actionable: (a) simulate communication latency/bandwidth and evaluate robustness; (b) define and report throughput metrics (tasks/hour) and the accuracy–throughput trade-off; (c) specify and evaluate conflict resolution when two agents write incompatible semantics simultaneously.

8. End-to-end latency and resource footprint underreported. Table 5 profiles TCSM update/query vs. voxel size, but excludes dominant costs from segmentation and LLM/VLM calls (Section 4.6). The reported memory usage (e.g., 6–9 GB at typical resolutions) and 249 ms query at 0.05 m may be challenging for embedded platforms. Actionable: report end-to-end action latency (including perception and LLM/VLM), CPU/GPU utilization over time, and a study on resource-constrained hardware or with model compression/caching.

9. Assumption of perfect localization without robustness analysis. The mapping requires agent pose P_t (Section 3.3) but there is no evaluation under odometry/pose noise, which is central to real deployments. Actionable: inject pose noise consistent with commodity SLAM drift and quantify impact on map accuracy and navigation metrics; consider simple pose-graph correction or loop-closure signals if available in Habitat.

10. Metrics and statistical reporting. While SR/SPL/SuccSPL are reported (Table 1; Fig. 3), there are no confidence intervals or variance across seeds/scenes, and some ablations use only a small subset (396 episodes in Table 4) without caveats. Actionable: provide per-scene variance or bootstrapped 95% CIs for all main tables/figures, and standardize evaluation set sizes across ablations to ensure comparability.

11. Scope of occlusion-specific analysis. BLOS is positioned to address occluded/disconnected targets (Section 3.4), yet there is no targeted benchmark slice that isolates such cases. Actionable: stratify episodes by occlusion/disconnectedness (e.g., targets in separate rooms) and report BLOS vs. base gains on that slice; include qualitative failure cases where BLOS harms performance.

12. Mixing regimes in comparisons is not transparent. The “Zero-Shot” column in Table 1 is empty for all methods, and some listed baselines are not strictly ZSON. Actionable: mark training regimes explicitly, separate ZSON-only vs. trained baselines, and ensure fair comparison policies (same sensors, action budgets, and language interfaces).

These changes would make the empirical claims more convincing, clarify the contributions of each component, and strengthen the case that the proposed PSM/TCSM/BLOS stack, rather than evaluation protocol advantages, drives the reported gains.

Suggestions/Questions:
1. Fairness of main SOTA comparison (Table 1; Section 4.2). Please clarify the evaluation protocol: your agent “operates sequentially across a series of tasks” with a persistent TCSM, whereas baselines “reset their state for each new episode.” Could you add:
   - A stateless variant of your method (TCSM disabled; otherwise identical pipeline) in Table 1.
   - “Memory-enabled” baselines (e.g., InstructNav/VLFM augmented with any persistent map they already maintain, or with your TCSM but without BLOS), reported under the same sequential protocol and step budget.
   - Exact step budgets, success radius, and whether LLM/VLM query limits are matched across methods.

2. Ambiguities in Table 3 (Section 4.5). The ablation table has duplicated/contradictory rows (two “InstructNav*”; two “TCSM+Weighted Update+Full Strategy” with very different scores) and an unlabeled “PSM Setting” column. Please correct labels, define “Replacement Update” vs. “Weighted Update,” state whether “Full Strategy” includes BLOS, and confirm all rows are evaluated on the same 2000 HM3D episodes with identical seeds. Confidence intervals or per-scene variance would help.

3. γ inconsistencies (Section 4.1 vs. Table 4). Implementation sets γ=0.2, yet text claims “0.8 yielded the most favorable results,” while Table 4 shows the best/tied best for GLEE at γ=0.2. Please reconcile:
   - What γ is used for the main results in Table 1 and ablations in Table 3?
   - Is γ dataset/backbone specific? If so, specify and justify the selection/tuning protocol.
   - Clarify the difference between the “GLEE” rows and the “GLEE (Wu et al., 2024) 0.2” row.

4. TCSM update rule details (Section 3.3; Eq. 2). The confidence dictionary D_i can grow and contains multiple classes per voxel. Please specify:
   - How you cap K_i (number of classes per voxel), whether you normalize confidences across classes, and if you apply decay to non-updated classes.
   - How you handle systematic mis-segmentation (e.g., persistent wrong class) and whether any outlier rejection or calibration is used beyond the fixed-rate blend.
   - Whether γ is adapted by c_pix, view angle, or depth uncertainty, or is strictly constant.

5. Robustness to drift/noise (Introduction; Section 3.3). You claim TCSM combats semantic drift with weighted updates. Could you add evidence beyond the “replacement vs. weighted” ablation in Table 3:
   - A stress test with controlled label noise injected into the segmentation outputs, plotting SR/SPL/SuccSPL vs. noise.
   - Map-quality metrics (per-voxel semantic precision/recall against ground-truth meshes) over long horizons to quantify drift accumulation.

6. Line-of-sight mechanics and failure modes (Section 3.4; Eq. 6). BLOS relies on LoS checks using PC_wall extracted from TCSM. Please detail:
   - The exact “wall” extraction procedure and thresholds from Fig. 2’s “Short-term Memory,” and how you mitigate incomplete walls.
   - How often PC′nav (proxy region) is non-empty, how frequently BLOS mode triggers, and the measured delta vs. the base strategy when it does.
   - An ablation with oracle LoS (from simulator mesh) to quantify headroom and typical failure cases when LoS is misestimated.

7. Occlusion/disconnectedness slice. Since BLOS targets occluded or disconnected targets (Section 3.4), could you report a stratified analysis (e.g., targets in separate rooms vs. same room) showing BLOS vs. base gains on that subset?

8. Pose error sensitivity (Section 3.3 uses pose P_t). How sensitive is mapping/planning to localization noise? Please add an experiment with injected odometry noise representative of commodity SLAM and report the impact on TCSM accuracy and navigation metrics.

9. Multi-agent concurrency details (Section 4.4; Table 2 labeled “Table 2” but referenced as “Tab. 4.4”). Please clarify:
   - Whether agents within a batch read each other’s updates in real time or only across batches (“shared memory persists across batches” suggests no in-batch sharing).
   - How simultaneous writes are merged and how conflicts are resolved.
   - Throughput metrics (tasks/hour) and the accuracy–throughput trade-off when enabling in-batch sharing with communication latency/bandwidth constraints.

10. End-to-end latency and resource profile (Section 4.6; Table 5). The compute analysis isolates TCSM update/query vs. voxel size. Could you provide:
   - Per-action end-to-end latency breakdown including segmentation (GLEE), LLM (Qwen‑Max), VLM (Qwen‑VL‑Max), LoS checks, and planning (A*), with median/95th percentiles.
   - GPU/CPU utilization over time and a study on lower-resource settings (e.g., smaller backbones or cached prompts).

11. Accuracy vs. voxel size. Table 5 gives timing and memory vs. voxel size but no accuracy. Can you report SR/SPL/SuccSPL vs. voxel size (e.g., 0.02/0.05/0.08/0.10 m) to expose the performance–cost trade-off?

12. Pre-existing memory protocol (Section 4.3; Fig. 3). Please clarify:
   - How the N prior tasks are sampled (categories, start-goal distribution), and whether their goals overlap with the held-out 500 tasks.
   - Whether any episodes from the evaluation set leak into the prepopulation pool.
   - How much spatial coverage the prepopulated TCSM achieves at each N (e.g., % navigable area mapped).

13. Zero-shot labeling in Table 1. The “Zero-Shot” column is empty. Please mark which baselines are ZSON vs. trained, and confirm that all methods share identical sensor modalities, action budgets, and success thresholds to ensure comparability.

14. Success threshold and stopping. Section 4.1 mentions a “preset distance” for success. Please report the numeric threshold and stopping criteria/timeouts used across all experiments.

15. Short-term memory construction specifics (Section 3.4). For PC_nav, PC_obs, PC_wall, PC_frontier, and PC_traj:
   - Provide concrete thresholds (height filtering, connectivity criteria) and parameters used to extract each point cloud.
   - Describe how PC_intu is produced from the VLM (“designated as PC_intu”) and whether you cache intuition directions across steps.

16. Dynamic environments and forgetting (Limitations: “Assumption of a Static Environment”). Do you have a simple mechanism (e.g., time-decay, change detection via inconsistency across revisits) that could be enabled now? Even a small-scale experiment with door states changing across tasks would be informative.

17. Reproducibility of LLM/VLM use (Section 4.1; Statements). Please include prompt templates, decoding parameters, temperatures, and seeding to ensure determinism across evaluations. If Qwen models are remote APIs, note any caching or rate limits.

18. Memory footprint control. Given Table 5’s RAM usage, how do you bound D_i size per voxel and overall map growth over very long sequences? Any pruning (e.g., top‑K classes per voxel, region-of-interest rolling windows) or compression you can share?

19. Reporting hygiene. There are cross-reference/typo issues (e.g., “Tab. 4.4,” “InsturctNav,” “acrooding”) and broken lines/duplications in the back matter. Please fix to avoid confusion, and ensure figure/table captions clearly define all symbols (e.g., c_sem in Eq. 4 and Eq. 8).

20. Code/artifact plan (Reproducibility statement). The statement appears truncated. For rebuttal, sharing evaluation scripts for SR/SPL/SuccSPL, data splits, and a minimal config to reproduce one HM3D scene with N prepopulation tasks would materially strengthen confidence.
